Pre-Processing:
   - choosing test dataset size for ML model development requires 2 different approaches for the 2 different metrics:
     - for hit rate and recall:
       success or fail for every test input as a discrete binary result is a Bernoulii process
       and the sum of the success follows a binomical distibution.
           The standard error of the accuracy is then the sqrt of the Binomial distribution variance:
              stderr = sqrt( (p*(1-p)) / N )
                 where N is test set size
              - choose accuracy of model p
                   e.g. p=0.90
              - choose the margin of error the experiment needs
                 e.g. E=0.01
                 e.g. E=0.005 for medical accuracy
              - detemine z from confidence interval or alpha (where alpha=1-confidence interval)
                  c.i.   z
                  0.8    1.28
                  0.9    1.64
                  0.95   1.96
                  0.99   2.56
                  0.999  3.29
               stderr^2 = (p*(1-p)) / N
                  where stderr = E/z
             N = (p*(1-p)) / (stderr^2)
                = z^2 * (p*(1-p)) / E^2
              e.g. for p=0.90 and E=0.01 and confidence interval=95%
                   N = 3458 samples
              e.g. for p=0.90 and E=0.005 (medical accuracy!) and confidence interval=95%
                   N = 13,830 samples
              e.g. for p=0.95 and E=0.005 (medical accuracy!) and confidence interval=95%
                   N = 7300 samples
                     so, if the model is more accurate, need fewer samples...
              e.g. for p=0.95 and E=0.10 and confidence interval=95%
                   N = 18
              e.g. for p=0.95 and E=0.05 and confidence interval=95%
                   N = 73
    - for NDCG@K metric:
        each test input has a continous scaler score NDCG@K y_i which is between 0 and 1 as output and so the
        standard error follows from the Cetnral Limit Theorem (the distr of the normalized sample
        mean converges to the standard normal distribution).
            mean(NDCG@K) = sample mean = (1/K) * sum_{i=1,N}(y_i) where y_i is the score for test_i.
            stderr = stdev / sqrt(N)
                where stdev = sqrt( (1/(N-1)) * sum_{i=1,N}( (y_i - mean(NDCG@K))^2 )
            - choose the margin of error the experiment needs
                 e.g. E=0.01
                 e.g. E=0.005 for medical accuracy
            - determine z from confidence interval or alpha (where alpha=1-confidence interval) of std normal distr.
                e.g. confidence interval 95% where alpha = 0.05
                for two tail significance use alpha/2
            - *also need an estimate of the expected population standard deviation of user-level NDCG@K scores.
               see below next section

            E = Z_{alpha/2} * stderr = Z_{alpha/2} * stdev / sqrt(N)

            ==> N = ( Z_{alpha/2} * stdev / E)^2

     - for stating that the NDCG@K metric of model A is better than model B by a minimum detectable effect:
       delta = mu_b - mu_a
       with statisticl power 1 - beta
          (e.g. 80% power)
       and signifcance level of alpha
          (e.g. 0.05)
       For paired test across same users:
          - N = (stdev_diff^2 * ( (Z_{alpha/2} + Z_beta)^2 ) / (delta^2)

          - choose delta as min diff in NDCG@K to detect (e.g. 0.005)
          - chose above Z_beta as the critical desired power (e.g. Z_0.2 ~ 0.84 for 80% power)
          - chose above A_{alpha/2} for 2-tailed significance (e.g. Z_{0.025} ~ 1.96}
          - stdev_diff is the std dev of the per-user differences scores (y_{B,i} - y_{A,i})
          - e.g. stdev=0.3, Z_al[ha/2=1.96, Z_0.2 = 0.84, delta=0.005,
                 N = 280
  - how to estimate stdev NDCG@K in 3 ways:
       (1) Historical or Pilot data:
           calc empiical sample stdev across test samples from a previous model:
               stdev = sqrt( (1/(M-1)) * sum_{i=1,M}( (y_i-y_mean)^2 )
               expect NDCG@10 stdev~0.35-0.45, NDG@20 stdev ~ 0.25-0.35, NDCG@100 stdev ~ 0.2-0.3
       (2) theoretcial upper bound (worst case)
           max possible variance is half the users get 1.0 and half get 0.1
              stdev_max^2 = 0.25
              stdev_max = 0.5
              ** use this for a conservative estimate of N
  - example estimates of test size N for NDCG@K metrics:
     - want NDCG@20 within a +-0.01 margin of error E, w/ 95% confidence (Z_{0.05/2}=1.96)
       and a stdev from baseline model eval : srdev=0.30
           N = ( Z_{alpha/2} * stdev / E)^2
             = (1.96 * 0.30 / 0.01)^2
             = 3_458
  ** The number of positive ratings in movie-lens MovieLens 1-M ratings.dat is 559444
     - val_HPO: validation partition to select best model in HPO needs to have
        N >= 1_000 ratings
        * caveat is that user and movie stratification may require more than 1_000

     - test_irred: test partition to estimate the irreducible error on the model
       algorithm after best params determined.  Estimation involves
       training through datasets of size N=10%, 25%, 50%, 75%, 100% of training data
       separately for a fresh model with best params
       and fitting the losses and N to a power-law in order to estimate the
       irreducible error as the projection to a very large N.
       To estimate the test size to calc irreducible error:
          - choose desired Margin of Error (MoE) at confidence level Z_{alpha/2} for the confidence
            N_test_irred = ((Z_{alpha/2} * gamma * stdev_loss)/MoE)^2
               where MoE is the max acceptable margin of error on irred error estimate c which is the irred error.
                     e.g.
                     MoE=0.002 for x accurate within +0.002 loss units.
                     stdev_loss is stdev of indev loss values (or metric idicators) across indev test samples.
                     Z_alpha/2 is critical z-score for desired conidence, e.g. Z=1.96 for 95% confidence;
                     gamma is extrapolaion inflation factor (gamma > 1) measures how much parameter variance
                     is magnfied when projecting c = lim_{N_train->inf}( E(N_train) )
                     in NonLinear least squares regression, we have
                        covar matrix of fitted params is Var(theta) = stdev_c^2 * (J^T * J)^-1 where J is the mx3 jacobian of
                        partial derivs evaluated on train sizes and stdev_E is stderr per point = stdev_loss/sqrt(N_val_irred)
               e.g. for continuous loss:
                   N_val_irred = ( (1.96 * 3.0 * 0.50) / (0.003) )^2
                               = 960_400 example instances
              NOTE: if measure the irred_error using a binary metric like hitrate or recall@k,
                    the stdev_loss is lower.  e.g. sqrt(p*(1-p) ~ 0.3-0.4
                    which can be nearly 3 times smaller N as a result, ~ 300_000 samples needed
              If my test dataset size is 50_000 samples, the wider margin of error (MoE) can be calculated:
                  MoE = (Z_{alpha/2} * gamma * stdev_loss) / sqrt(N_test)
                      e.g. if we use a 96% confidence, hence Z=1.96 and an inflation factor gamma=3.0
                      then for a continuous loss metric and an assumption of stdec_loss=0.5
                         MoE = (1.96 * 3.0 * 0.5)/sqrt(50_000) = 2.95 / 223.6 ~ 0.013
                         so we'd expect the estimated irred loss to be accurate within += 0.01
     - test parition size determined by
       N = ( Z_{alpha/2} * stdev / E)^2
       N >= 5_000.
        * caveat is that user and movie stratification may require more than 5_000
          see docs/mlops/movie_tier_counts.txt
          if the script count_movie_tiers::test_explore_movie_stratification_for_splits

           for each user, split their ratings by timestamp into 80:10:10 percentages.

  - the first versions of the pipeline used data splits by timestamp into
     80:10:10 for train, val, test and did not filter for rare users or rare movies.
     the result was that there was not enough overlap in tail distribution
     between training and validation.
   - the corrected final split uses a partition on a per user basis where each user's ratings are ordered by
     their timestamps and placed 80:10:10 into train, val, and test, respectively.
   - users and movies with fewer than 30 ratings are dropped
   - consider splitting the data into 4 partitions to keep an untouched extra validation dataset for
     use in estimating the irreducible error.  The irreduclbe error can be calculated once a
     trained healthy model is made.
   
   - NOTE: for large applications, a more common approach to data splitting uses a rolling time
     window to continuously keep training the model.
     to avoid catastrophic forgetting of data older than the train time window and to keep
     information about seasonality, one usually adds a random sample of history from past 1+ years
     for each user.  the validation dataset is strictly greater in time that the train dataset,
     and the test dataset is strictly greater in time than the validation dataset.
     and occassionaly, the model has to be scrapped and trained from scratch on the latest
     data.

   - after have designed model, can examine whether the train, val, and test sizes are enough to well
     determine the trainable parameters.  The estimate here use the positives ratings of the dataset only in estimates.
     the TwoTowerDNN model number of trainable parameters = 86_394.
     (1) the layers in the model which process a single interacation are :
        dense_query: 4_992 parameters
        dense_candidate: 3_200 parameters
        There are more than 8192 ratings in the train dataset, even for the user_tier and movie_tier stratifications
          #positive train ratings / parameter = 459_148 / 8_192 = 56 observations per parameter which is great
          then do the same for the smallest stratification, the number of user_tier=2 ratings in train:
                = 41405 / 8192 = 5 which is decent
          so these are strongly over-determined which is good
      (2) Sparse embedding parameters
           these are the majority of the model weights, 31_216 + 54_388 = 85_604.
           let k_i = per entity sample counts
           we calc k_i / embedding dimension
           recommender interaction counts follow a power-law (Zipfian) distribution:
               head entities with many ratings have k_i/emb_dim >> 1
               tail counts have k_i/emb_dim ~ 1 and a little higher
               cold start entities entites with 0 to few ratings (e.g. < 30) have k_i/emb_dim < 1
                   so these tail/cold star entities are at risk of being severely underdetermined
                   leading to high variance (over-fitting) and the model might just memorize them.
               all except the cold entities are well determined
          ***===> NOTE here we can see that increasing the embedding length to be larger than 32 would
                  make more than the cold start entities underdetermined, and presumably would lead to more over-fitting.

Pipeline pre-processing and transformation:
- data ingestion:
  - apache beam components in TFX pipeline are highly distibutable
  and there are options and many examples on how to make custom
  components with dsl annotatings as needed
  - a custom component is needed to join the ratings records
    with user and movie information.
- transformations
  - normalizing rating to a relevance value between 0 and 1
  - transforming timestamp into features that might be used in the model
    such as year, and a cross between hour of day and weekday.
  - cateogorization needed for renumber
  - options for library to use:
    - tf.data is for in-memory size data processing so not an option here.
    - considered using keras layers
      pros:
        - less code, simpler to maintain
      cons:
       - by performing the transformation to features in the model, we are
         repeating work, especially during the compute intensive hyper-parameter
         tuning phase.
       - features, that is, tranformed data, are not saved in a feature store
       - cannot perform stats on features
    - decided to use tft and tfx
      pros:
        - transform to features once and that is input to the hyper-parameter tuning
        - transformed data is persisted and usable in calculating statistics
      cons:
        - ramping-up to using it is larger

pipeline:
  - decided on TFX 
    - scalability, works on linux in all environments, is a mature platform with
      alot of documentation, examples, community support
    - the pipeline can be compiled to create a yaml intermediate file
      for running with airflow or kfp, etc.  cloud specific changes
      for Vertex AI, etc. should be straight forward.
  - the components needed in the pipeline to implement the requirements:
    - MovieLensExampleGen: a custom ingest component that joins ratings with 
      user and movie data
    - Resolver for resolving artifacts in the MLMD datastore
    - StatisticsGen for calculating stats on the transformed data
    - SchemaGen for extracting a schema from the statistics
    - Importer for inporting a schema when needed
    - ExampleValidator for anomaly and missing value detection
    - ExampleDiff for looking for data skew compared to previous data
    - Tranform to perform data transformations
    - Tuner to find hyper-parameters for best performing model
    - Trainer to train a model using the best hyper-parameters
    - Evaluator for calculating model eval stats and a quality 
      validation w.r.t. a baseline model
    - optionally: InfraValidator to validate that the model 
      is compatible with the serving infrastructure.
    - Pusher for pushing a blessed model to the serving_model directory
    - BulkInferrerBeam: a custom component to handle specifics for saved_model

monitoring:
  - any metrics monitored outside of the pipeline, for a model actively
    serving inference.

listwise evaluation metrics:
  - comparing current model to previous:
    - normalized hit rate (NHR)
  - comparing each model in the series of Retrieval, Ranking, and Re-Ranking
    for improvments in ability to provide relevant ranked recommendations
    to a user:
    - NHR, NDCG@K, recall_tail@K, and intra-list diversity

Misc:
  - ability to write data in formats: tfrecord, parquet, and array_record
    for downstream components

Late item of interest regarding data preparation before
the pipeline:
   - movie ids are rewritten from src/main/resources/ml-1m-orig/
     to src/main/resources/ml-1m/ by script
     src/test/python/movie_lens_tfx/RenumberIds.py
     - the movie ids are reassigned numbers that start at n_users + 1
       and continue consecutively to n_user + n_movies + 1.
     - the reason that the re-numbering is needed is because a
       downstrem component, the Ranker, needs the movie ids to follow
       the user ids in numerical order as they are both used as
       indices (offset by 1) for accessing a matrix of concatenated 
       user_embeddings followed by movie_embeddings.
